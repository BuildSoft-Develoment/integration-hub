## Alcance del documento

Este documento resume como se usa `SDD` en el proyecto real. Las specs oficiales viven en `specs/`, pero la regla de construccion y trazabilidad se define aqui.

## Estado actual de SDD

- El backlog ejecutable del producto se organiza en carpetas numeradas dentro de `specs/`.
- Cada feature mantiene tres artefactos obligatorios: `spec-funcional.md`, `spec-tecnica.md` y `spec-tareas.md`.
- Las features actuales cubren catalogos, readers, diseno de procesos y observabilidad/auditoria.
- `QA`, `Ops` y `Releases` deben poder seguir la misma feature sin reinterpretar nombres o alcance.

## Entrada minima

- requerimiento o historia priorizada
- reglas funcionales y actores identificados
- impacto arquitectonico conocido o aclarado con `ADR`
- fase UX/UI suficientemente clara cuando afecta pantallas o flujos

## Flujo estandar aplicado

1. Capacidad priorizada desde requerimientos o backlog.
2. Carpeta de feature creada en `specs/<nnn-feature>/`.
3. Redaccion de `spec-funcional.md`.
4. Redaccion de `spec-tecnica.md`.
5. Derivacion de `spec-tareas.md`.
6. Implementacion y pruebas en el modulo que corresponda segun la frontera motor/vertical
   (ADR-021). El reactor tiene siete modulos y NO todo va a `platform-app/`: ver
   [estructura real del repositorio](../transversal/90.06-estructura-repositorio-real.md).
7. Evidencia de QA y consideraciones de deploy/operacion.

## Que cambia entre requerimientos y specs

| Artefacto | Pregunta que responde | Aterrizaje en este proyecto |
| --- | --- | --- |
| requerimiento | que necesita el producto | modulos, casos de uso e historias en fase 1 |
| spec funcional | como debe comportarse una feature concreta | flujo, criterios de aceptacion y casos borde |
| spec tecnica | como se implementa la feature | contratos, datos, seguridad, observabilidad, riesgos |
| spec de tareas | que trabajo debe ejecutarse | backlog implementable por rol y capa tecnica |

## Reglas de trazabilidad

- toda feature debe nacer en `specs/`
- si la feature cambia arquitectura, debe registrar o actualizar `ADR`
- QA debe dejar casos y evidencia trazables a la feature
- deploy y operacion deben reflejar impacto en `ops/` y `releases/` cuando corresponda

### Como se materializa en el codigo

Las reglas de arriba son principios; **el mecanismo que las hace verificables no estaba escrito en
ninguna parte de esta fase**, pese a haber 265 anotaciones en el repositorio.

El codigo declara su trazabilidad con anotaciones en comentario:

```java
/**
 * @trace spec 008-mensajeria-pagos RF-004, T-009
 * @covers ADR-021
 */
```

- **`@trace`** apunta al requisito o tarea que ese codigo implementa.
- **`@covers`** apunta a la decision de arquitectura que respeta.

**Cualificar siempre la referencia.** Las ocho features numeran sus requisitos localmente
(`RF-001`, `RF-002`...), asi que un `@trace RF-004` a secas es **ambiguo entre ocho features**. La
forma correcta incluye la spec: `@trace spec 008-mensajeria-pagos RF-004`.

### Los validadores que lo comprueban

En `ci/scripts/`, encadenados a `npm run check:all`:

| Validador | Que comprueba |
|---|---|
| `check-trace-drift.mjs` | Que cada enlace de trazabilidad declarado resuelve a algo que existe. |
| `check-trace-coverage.mjs` | Que cada requisito con codigo declarado tiene al menos un `@trace`. |
| `check-api-vs-code.mjs` | Que los endpoints del codigo estan en el contrato OpenAPI. |
| `check-rbac-vs-code.mjs` | Que los roles de `@RolesAllowed` estan en la matriz del ADR. |
| `gen-catalogo-tipos.mjs --check` | Que el catalogo de tipos documentado coincide con el codigo. |

> **Advertencia historica.** Hasta el 2026-07-31 el harvest solo escaneaba `platform-app`, asi que
> las anotaciones de los verticales -incluidas las 72 del money-path- eran invisibles y el gate daba
> verde sin haberlas mirado. La lista de raices es ahora unica:
> `ci/scripts/_lib/source-roots.mjs`. Al anadir un modulo al reactor, anadirlo ahi.
