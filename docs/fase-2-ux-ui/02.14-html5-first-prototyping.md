## Objetivo
Acelerar la validacion UX generando prototipos HTML5 navegables desde SPDD antes de formalizar diseno en Penpot o construir Angular.

## Regla
HTML5-first es un prototipo, no frontend productivo.

No se pasa a SDD final ni a construccion frontend productiva sin prototipo validado. El prototipo puede ser HTML5, Penpot, wireframe aprobado o mockup validado, pero para iteracion rapida se recomienda HTML5 primero.

Por defecto, el prototipo HTML5 debe ser un `index.html` autocontenido: HTML5 semantico, CSS responsive y JavaScript vanilla dentro del mismo archivo. Esto maximiza portabilidad: debe funcionar abriendo `index.html` en el navegador, sin build, sin backend y sin dependencias externas.

## Estandar producto-real
Para productos completos, HTML5-first debe generar un portafolio de prototipos por vertical funcional, no un unico prototipo monolitico. El hub `/prototype/index.html` debe presentar journeys, cobertura y estado de gates, y cada spec visual debe tener su propio `prototype-html5/index.html`.

Ver el estandar obligatorio: [02.15-estandar-prototipo-html5-producto-real.md](02.15-estandar-prototipo-html5-producto-real.md).

## Lenguaje visible de producto
El prototipo por spec no debe mostrar etiquetas metodologicas como navegacion o encabezados de pantalla. Palabras como `Recorrido`, `Resumen`, `Actividad de ejemplo`, `Formulario-spec`, `Contrato mock`, `RF`, `gate`, rutas o componentes pertenecen a la documentacion, no a la UI del producto.

El agente debe traducir cada seccion visible a lenguaje del dominio:
- autenticacion: `Datos de la cuenta`, `Activacion familiar`, `Perfiles`;
- streaming: `Filtros y preferencias`, `Reproduccion`, `Episodios`;
- control parental: `Reglas familiares`, `Solicitudes`, `Salida protegida`;
- busqueda: `Filtros de busqueda`, `Resultados`, `Recientes`;
- favoritos/historial: `Continuar viendo`, `Mi lista`, `Actividad familiar`;
- devocional: `Reflexion del dia`, `Progreso diario`, `Musica`;
- backoffice: `Ficha de contenido`, `Historial editorial`, `Publicacion`;
- notificaciones: `Preferencias de aviso`, `Prueba de aviso`, `Horarios`;
- seguridad: `Filtro de alertas`, `Seguimiento`, `Actividad sensible`.

Regla practica: si el label sirve para explicar la metodologia al proveedor IA, no debe estar visible en el HTML5 de la spec.

### Separacion hub vs prototipo por spec

El hub `/prototype/index.html` y los documentos SPDD pueden mostrar cobertura, RF, estado de gates y checklist porque son artefactos de gobierno del delivery. El prototipo navegable por spec (`specs/<feature>/prototype-html5/index.html`) debe hablar como producto.

Por tanto, no uses botones o tabs visibles como `Cobertura`, `Estados UI`, `Simular loading`, `Simular empty`, `Simular error`, `Simular success` o `Acceso denegado` para demostrar cumplimiento. Convierte esos casos en acciones naturales del dominio: buscar sin resultados, actualizar datos, reintentar una carga, guardar una decision, reproducir un contenido, aprobar una ficha o intentar una accion que requiere permiso.

La estructura visual se decide por dominio, no por una prohibicion fija de componentes. Un timeline es valido si es un patron natural del producto: tracking de pedido, historial clinico, auditoria, seguimiento de caso, roadmap, despliegue, expediente, ticket o actividad operacional.

Lo que se bloquea es el timeline generico usado para explicar la metodologia o disfrazar una lista de pasos. Si aparece una linea de tiempo, debe tener datos mock del dominio, estados reales del producto, eventos clicables y acciones coherentes. Si el dominio no necesita timeline, el avance debe convertirse en otro componente de producto: player con progreso, cola de revision, resultados, solicitudes, vista previa, actividad reciente o seguimiento operativo.

## Sistema visual compartido
Los prototipos por spec pueden tener acentos por vertical, pero deben respetar un sistema visual comun del producto: misma topbar/base de marca, tipografia, escala de espaciado, radios, sombras, tokens de fondo, color de confirmacion/error y tratamiento de botones.

Direccion base esperada por proyecto:
- definir tokens de marca del producto instanciado antes de generar prototipos;
- mantener fondo, superficies, contraste y jerarquia visual coherentes entre verticales;
- usar un color de accion primaria comun para todo el portafolio;
- permitir acentos secundarios por spec solo para identificar vertical, sin romper identidad;
- reutilizar el mismo tratamiento de botones, paneles, modales, toasts, formularios y estados;
- mantener datos mock consistentes entre specs: actores, nombres, fechas, estados, contenidos y reglas deben pertenecer al mismo universo de producto.

## Arquitectura de navegacion obligatoria
Todo proyecto con prototipos HTML5 debe tener un unico punto de entrada navegable en `/prototype/index.html`. Este archivo funciona como hub/guia end-to-end del producto: muestra el journey recomendado, enlaza a cada feature y permite entender el mapa completo sin abrir carpetas manualmente.

La navegacion debe ser bidireccional:

```text
/prototype/index.html  <->  /specs/<feature>/prototype-html5/index.html
```

Reglas:
- `/prototype/index.html` es el hub end-to-end y debe enlazar a todos los prototipos HTML5 por spec.
- `/prototype/index.html` debe cubrir estas secciones minimas: `Journey end-to-end`, `Prototipos por spec`, `Actores del sistema` y `Estado del prototipo/Cobertura`.
- Cada `specs/<feature>/prototype-html5/index.html` debe incluir un enlace visible para volver a `/prototype/index.html`.
- Cada spec debe tener su propio prototipo enfocado en sus RF; no debe ser una copia completa del hub ni del prototipo de otra feature.
- El prototipo de cada spec debe verse como una porcion real del producto, con actor, accion principal, estados, permisos, validaciones y feedback propios de esa feature.
- El hub puede ser una guia de recorrido, pero no reemplaza la evidencia navegable especifica de cada feature.
- No se deben crear puntos de entrada paralelos que compitan con `/prototype/index.html` salvo excepcion documentada.

## Criterio minimo UX
Para que el prototipo sirva como evidencia real, no basta con una pantalla bonita. Debe permitir validar el flujo completo, los estados, los permisos y el feedback de usuario.

| Elemento | Debe demostrar |
|---|---|
| Flujo | Journey principal extremo a extremo, por ejemplo login -> busqueda -> generacion -> estado -> descarga |
| Estados | Cargando, error, exito, sin resultados y permiso denegado cuando aplique |
| Validaciones | Campos obligatorios, fechas requeridas, rangos invalidos y reglas de negocio visibles |
| Roles | Diferencias de experiencia para admin, operador, auditor u otros roles del dominio |
| Datos fake | Tablas, formularios, filtros, historial y resultados mock representativos |
| Navegacion | Menu lateral, tabs, botones, breadcrumb o equivalentes segun el producto |
| Feedback UX | Toast, modal, confirmacion, progreso y mensajes recuperables |

Si el prototipo no permite revisar estos puntos, no esta listo para `gate-prototype-ready`.

## Decision de producto por defecto
El prototipo HTML5 debe sentirse como un corte vertical del producto real, no como una consola generica de checklist. La decision por defecto es crear una experiencia especifica de la feature y del dominio, con composicion, navegacion y lenguaje visual propios del producto que se esta validando.

Para una plataforma de streaming, por ejemplo, el prototipo esperado no es un dashboard lateral generico. Debe parecer una plataforma de contenido: topbar de marca, buscador, selector de perfiles, hero de contenido destacado, carruseles o grilla de posters, filtros por edad/tema, detalle de video, modal o vista de reproduccion, progreso y bloqueo parental visible.

Para una herramienta operativa, en cambio, si corresponde un patron de producto operativo: toolbar, tabla principal, filtros, detalle, acciones, confirmaciones, historial y estados de proceso. La forma visual se decide por el dominio, no por comodidad del agente.

### Regla de prioridad producto sobre cobertura
Cubrir RF no autoriza a crear una shell generica. La cobertura debe mapearse en el hub y documentos, mientras que el prototipo por spec debe comportarse como producto.

Ejemplo para streaming:

```text
Incorrecto:
Sidenav -> Inicio/Catalogo/Reproductor -> tabla -> formulario -> confirmar accion

Correcto:
Topbar de marca -> perfil activo -> hero -> filtros -> posters -> detalle -> reproducir -> player/progreso
```

Ejemplo para reproductor:

```text
Incorrecto:
Panel con pasos "detalle abierto, audio seleccionado, subtitulos configurados"

Correcto:
Player 16:9 -> play/pause -> seek -> volumen -> calidad/subtitulos -> lista de episodios -> autoplay
```

Los estados `loading`, `empty`, `error`, `permission denied`, `success` y `progress` deben existir como comportamiento activable o contextual. No deben aparecer como una lista de pantallas artificiales si eso rompe la ilusion de producto.

### Jerarquia de decisiones
| Decision | Prioridad | Criterio |
|---|---:|---|
| Corte vertical de producto | 1 | El usuario puede recorrer una tarea real de principio a fin. |
| Look and feel del dominio | 2 | La pantalla parece pertenecer al producto descrito, no a una plantilla generica. |
| Cobertura funcional | 3 | RF, roles, estados, validaciones y feedback estan activables. |
| Autocontenido | 4 | Abre sin build, backend ni dependencias externas. |
| Amplitud de modulos | 5 | Cubrir muchos modulos solo si no destruye la claridad del flujo principal. |

Regla practica: si un stakeholder abre el HTML y no entiende que producto esta viendo en los primeros 10 segundos, el prototipo no esta listo aunque tenga botones para estados.

## Regla de separacion visual
El hub y la documentacion pueden mostrar RF, RN, roles, permisos, gates, matriz de cobertura y decisiones tecnicas. El HTML5 de cada spec no debe mostrar esos codigos como contenido visible. Debe mostrar el producto funcionando con datos mock.

Ejemplo:

```text
Incorrecto en spec HTML5:
"RF-04", "CRISTIANO_CONTENT_VIEW", "gate-prototype-ready", "CatalogRowComponent"

Correcto en spec HTML5:
"Perfil infantil", "Contenido recomendado", "Edad permitida", "Agregar a mi lista", "Necesitas autorizacion familiar para ver este contenido"
```

Si el agente necesita dejar trazabilidad tecnica, debe ponerla en `spdd-frontend.md`, `traceability.md`, `decisiones-ux.md` o en el hub, no como UI del prototipo.

## Flujo recomendado
```text
Product Design
  -> SPDD
  -> HTML5 Prototype navegable
  -> Prototype Validation
  -> Penpot si aplica diseno formal
  -> gate-spdd-approved
  -> SDD
  -> Angular real + Backend
```

## Cuando usar HTML5
- Validar flujo rapido con negocio.
- Probar navegacion entre pantallas.
- Simular estados UI.
- Mostrar permisos, mensajes, errores y restricciones.
- Crear un mock navegable versionado en Git.
- Iterar con IA antes de invertir en diseno visual formal.
- Validar procesos empresariales antes de Angular/Nx/microfrontends.
- Simular formularios, tablas, modales, toasts, jobs asincronos y descargas mock.

## Cuando no usarlo como salida final
- El proyecto exige design system formal.
- El equipo UX requiere revision visual en Penpot.
- Hay handoff visual a multiples equipos.
- Se necesita aprobacion de marca o accesibilidad visual detallada.
- Ya existe Penpot aprobado.

## Estructura sugerida
```text
prototype/
  index.html                # hub/guia end-to-end del producto
  README.md
  rf-coverage.md            # recomendado cuando hay multiples RF

specs/<feature>/
  product-design.md
  spdd-frontend.md
  prototype.md
  prototype-validation.md
  ui-test-cases.md
  prototype-html5/
    index.html              # archivo unico autocontenido por defecto
    flujo.md
    decisiones-ux.md
```

Para flujos complejos tambien se permiten archivos separados, pero solo si se documenta la razon en `decisiones-ux.md`:

```text
prototype-html5/
  index.html
  styles.css
  app.js
  mock-data.js
  flujo.md
  decisiones-ux.md
```

## Perfil visual recomendado
- Diseno orientado al dominio: streaming, SaaS operativo, CRM, e-commerce, educacion, salud u otro patron reconocible.
- Toolbar superior, sidenav, tabs, hero, carruseles, cards, tablas o formularios segun el producto; no imponer un shell generico.
- Para productos de contenido o consumo, priorizar portada, selector de perfil, busqueda, catalogo visual, detalle y reproduccion/accion principal.
- Para productos operativos, priorizar densidad, filtros, tablas, detalle, acciones y estados de proceso.
- Estilo inspirado en Angular Material cuando el frontend futuro sea Angular, sin perder identidad de producto.
- Modo claro/oscuro simulado si ayuda a validar preferencia visual.
- Sin frameworks externos por defecto.
- Tailwind via CDN solo si el PO necesita velocidad visual y se declara como decision temporal.

## Estados minimos a simular
- `loading`
- `empty`
- `error`
- `permission denied` o `unauthorized`
- `success` cuando exista accion confirmable
- `in progress` cuando exista proceso asincrono, job o descarga diferida
- restricciones de permisos o reglas visibles

## Interacciones minimas esperadas
- Navegacion simulada entre pantallas o vistas.
- Breadcrumb, menu lateral, tabs o patron equivalente cuando el flujo tenga varias secciones.
- Validaciones de formulario visibles.
- Diferencias por rol o perfil visibles si la feature cambia por usuario, usando lenguaje del producto y no permisos tecnicos.
- Modal de confirmacion cuando la accion sea irreversible, asincrona o sensible.
- Toast o notificacion para exito/error.
- Indicador de progreso cuando se simule generacion, carga, job o descarga.
- Tabla de historial cuando el flujo tenga jobs, descargas, auditoria o eventos.
- Timeline solo cuando sea patron natural del dominio; si no aplica, usar resultados, cola, player, solicitudes, vista previa, actividad reciente o seguimiento.
- Mapeo tecnico hacia Angular documentado en `spdd-frontend.md` o `decisiones-ux.md`; el prototipo visible no debe depender de textos tecnicos.

## Evidencia requerida
- `/prototype/index.html` creado como punto de entrada end-to-end del producto.
- Navegacion bidireccional entre `/prototype/index.html` y `specs/<feature>/prototype-html5/index.html`.
- `prototype-html5/index.html` creado y autocontenido, salvo excepcion documentada.
- El prototipo de la spec es propio de la feature y no una copia completa del hub.
- El prototipo de la spec se ve como producto real segun el dominio, no como artefacto documental generico.
- archivo de flujo en `specs/<feature>/prototype-html5/` con navegacion y pantallas.
- archivo de decisiones UX en `specs/<feature>/prototype-html5/` con decisiones, supuestos y limitaciones.
- Navegacion funcional entre pantallas o vistas.
- Estados UI visibles.
- Diferencias por rol/perfil visibles cuando sean parte de la feature, sin exponer permisos tecnicos.
- Validaciones y feedback UX activables.
- Datos mock identificados como mock.
- Ruta registrada en `prototype.md`.
- Limitaciones registradas.
- Validacion registrada en `prototype-validation.md`.

## Red flags
- No existe `/prototype/index.html` como punto de entrada end-to-end.
- La navegacion entre `/prototype/index.html` y `specs/<feature>/prototype-html5/index.html` no es bidireccional.
- Los prototipos por spec son copias identicas del hub o de otras specs.
- El prototipo de la spec no parece una feature real del producto.
- El prototipo parece un dashboard generico aunque el dominio sea streaming, educacion, marketplace u otro producto con patrones visuales propios.
- El agente prioriza cubrir muchos RF en una sola shell y pierde el flujo principal de producto.
- El agente muestra RF, estados o validaciones como etiquetas de checklist dentro de la pantalla, en vez de convertirlos en interacciones naturales.
- La navegacion usa labels genericos como `Resumen`, `Actividad de ejemplo` o `Recorrido simulado` sin significado de producto.
- Para streaming/catalogo no existe topbar, perfil, busqueda/filtros, posters, detalle y accion de reproduccion.
- Para reproductor no existe player, controles, progreso, episodios o autoplay.
- El primer viewport no comunica el producto, actor y accion principal.
- El prototipo no navega.
- No hay estados `empty`, `error` o permisos.
- No se ven roles, permisos o diferencias de acceso cuando el dominio los exige.
- No hay validaciones ni feedback para acciones importantes.
- Falta progreso en flujos asincronos o de descarga.
- Se confunde HTML5 con Angular productivo.
- El prototipo depende de backend, build o paquetes no documentados.
- Se separan muchos archivos sin razon operacional.
- El prototipo no esta registrado en `prototype.md`.
- `prototype-validation.md` queda vacio o sin responsable de validacion.

## Calidad minima exigida

Todo prototipo HTML5 generado por agente de IA debe alcanzar **nivel 2 o nivel 3** segun la rubrica antes de poder avanzar al gate. Un prototipo en nivel 0 o nivel 1 debe ser rehecho.

Ver clasificacion completa: [02.16 Rubrica de Calidad](02.16-rubrica-calidad-prototipo-html5.md).
