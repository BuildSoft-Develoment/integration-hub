## Objetivo

Definir como usar agentes, prompts y skills en este repositorio sin perder trazabilidad, gobierno ni consistencia documental.

## Que debe leer la IA

- `docs/fase-0-iniciacion/00.01-vision-proyecto.md`

- `docs/fase-0-iniciacion/00.04-roles-y-responsabilidades.md`
- `docs/transversal/90.10-entregables-minimos-por-fase.md`
- `docs/transversal/90.13-modos-de-trabajo.md`

Si la tarea afecta arquitectura, tambien debe revisar:

- `docs/fase-3-arquitectura/03.00-arquitectura.md`

## Diferencia entre agente, prompt y skill

| Artefacto | Para que sirve | Cuando usarlo |
| --- | --- | --- |
| Agente | representa un rol especializado | cuando se necesita una salida integral por fase o dominio |
| Prompt | instruccion reutilizable para un entregable concreto | cuando ya se conoce el artefacto a producir |
| Skill | capacidad reusable de trabajo o revision | cuando se quiere repetir una forma de ejecutar o validar |

## Reglas obligatorias

- La IA no debe inventar decisiones tecnicas sin `ADR` o justificacion explicita.
- Toda salida de IA debe terminar en una ruta canonica del repositorio.
- Los prompts no reemplazan documentos oficiales; los producen o actualizan.
- Los skills deben reforzar consistencia, no sustituir analisis ni validacion humana.
- Si una salida cambia arquitectura o tecnologia, debe reflejarse en fase `3` o en `ADR`.
- Si la IA opera en `modo exploratorio`, debe cerrar con recomendacion y siguiente paso formal.
- Si la IA opera en `modo estructurado`, debe actualizar directamente artefactos oficiales.

## Formato de salida esperado

- Para planificacion: roadmap, estimacion, riesgos y roles.
- Para arquitectura: markdown, `ADR`, `LikeC4` y despliegue.
- Para `SDD`: `spec funcional`, `spec tecnica` y `spec de tareas`.
- Para construccion: componentes afectados, pruebas y trazabilidad a specs.
- Para QA y ops: casos, evidencias, checks de deploy y metricas.
