## Objetivo

Ser la **fuente canonica** de que fuentes, readers y tipos de tarea existen en el producto.

## Por que este documento se genera solo

La auditoria de las nueve fases encontro el mismo error repetido en seis documentos: enumeraban
"4 fuentes" cuando hay 8, un punado de tipos de tarea cuando hay muchos mas, y readers que desde
ADR-021 ya no viven en el motor.

El problema no era la redaccion. Era el **formato**: una lista escrita a mano caduca el dia que
alguien registra el noveno provider, y nadie vuelve a los seis sitios a corregirla. Corregir las seis
listas solo habria reiniciado el reloj.

Por eso ninguna fase vuelve a enumerar tipos. Cada fase declara el **mecanismo** —el catalogo es dato
en runtime, los providers se registran por CDI y el motor los descubre— y enlaza aqui. Y aqui el
contenido lo pone el codigo, no una persona.

## Como se regenera

```bash
npm run gen:catalogo          # reescribe la zona de abajo
npm run gen:catalogo:check    # falla si esta desactualizada (lo corre el CI)
```

El generador (`ci/scripts/gen-catalogo-tipos.mjs`) recorre los modulos Java del reactor y lee el tipo
que cada provider declara. Si un provider calcula su tipo en runtime, se reporta como `(dinamico)` en
vez de inventar un valor: es preferible un hueco visible a un catalogo que miente.

## Extensibilidad

Esta lista **no es cerrada**. `TaskType.BUILTIN` enumera solo los tipos del motor; los verticales y
los plugins registran los suyos via `TaskProviderRegistry` sin tocar el nucleo. Que la tabla crezca al
anadir un vertical es el comportamiento correcto, no una anomalia.
