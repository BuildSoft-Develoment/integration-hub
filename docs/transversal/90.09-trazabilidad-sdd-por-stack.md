## Objetivo

Conectar el stack vigente del proyecto con la forma concreta en que se materializan features bajo `SDD`.

## Trazabilidad vigente

Las features del proyecto ya mantienen una cadena esperada entre requerimiento, arquitectura, construccion, calidad y operacion:

- `docs/fase-1-analisis-requerimientos/`
- `docs/fase-3-arquitectura/`
- `specs/001-catalogo-fuentes/`
- `specs/002-catalogo-readers/`
- `specs/003-diseno-y-ejecucion-procesos/`
- `specs/004-observabilidad-y-auditoria/`
- `specs/005-catalogo-conexiones/`
- `specs/006-programacion-procesos/`
- `specs/007-tema-del-sistema/`
- `specs/008-mensajeria-pagos/`
- `qa/fase-6-qa/`
- `ops/fase-7-deploy/`
- `ops/fase-8-operacion/`

## Regla de uso

- cada feature nueva debe partir de una carpeta propia en `specs/`
- cada feature debe mantener `spec-funcional.md`, `spec-tecnica.md` y `spec-tareas.md`
- la implementacion debe poder localizarse en el modulo que le corresponda segun la frontera
  motor/vertical: son **siete modulos**, no uno. Ver
  [estructura del repositorio](90.06-estructura-repositorio-real.md)
- las anotaciones `@trace` / `@covers` del codigo deben **cualificar la spec**
  (`@trace spec 008-mensajeria-pagos RF-004`), porque cada feature numera sus requisitos localmente
  y un `RF-004` a secas es ambiguo entre ocho
- QA y Ops deben poder seguir la misma numeracion o nombre funcional cuando el cambio lo requiera

## Regla de integridad

Si una feature existe en `specs/` pero no puede rastrearse en codigo, calidad o operacion, la trazabilidad esta incompleta.
