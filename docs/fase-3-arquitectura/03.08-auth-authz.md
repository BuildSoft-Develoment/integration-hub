<a id="objetivo"></a>
## Objetivo
Dejar explicito el baseline de autenticacion y autorizacion del Integration Hub (backend Quarkus + frontend Angular, identidad con Keycloak/OIDC), con la matriz de roles reales (los cinco transversales mas los dos del four-eyes bancario; ver la matriz de abajo) y su detalle canonico endpoint x rol en [ADR-003](adr/ADR-003-rbac-endpoint-rol.md).

<a id="authn-baseline-jwt-firmado-oidc"></a>
## AuthN baseline: JWT firmado OIDC
- Protocolo: OAuth 2.1 / OpenID Connect para login interactivo y Client Credentials para servicio-a-servicio.
- Formato de token: JWT firmado RS256 o ES256. HS256 solo permitido en ambientes dev locales.
- Descubrimiento: `/.well-known/openid-configuration` del IdP con JWKS publico.
- Vida del access token: 10-15 minutos.
- Refresh token: rotacion obligatoria (cada uso invalida el anterior).
- PKCE obligatorio en flujos interactivos.

Claims estandar esperados en el access token:
- `sub` (subject, identificador estable del usuario).
- `aud` (audience, debe incluir el servicio consumidor).
- `iss` (issuer URL del IdP).
- `exp`, `iat`, `nbf`.
- `scope` (string con scopes separados por espacio).
- `tenant_id` o equivalente para multi-tenant.

Claims adicionales custom:
- `roles` (array de strings con roles del usuario).
- `groups` (array de strings con grupos Backstage/LDAP).
- `session_id` (para auditoria y logout distribuido).

<a id="authz-baseline-rbac-mas-claims"></a>
## AuthZ baseline: RBAC mas claims
- RBAC como estructura base: roles agrupan permisos; usuarios se asignan a roles.
- Atributos adicionales (ABAC) se evaluan solo cuando RBAC no basta (ej. "solo puede ver recursos de su region").
- Los permisos se expresan como acciones sobre el recurso de dominio primario del Integration Hub —el proceso de integracion—: `process:read`, `process:write`, `process:approve`. Los recursos secundarios (catalogo) siguen el mismo patron: `source:read/write`, `reader:read/write`, `connection:read/write`.
- El token porta roles; el servicio resuelve permisos localmente a partir de la tabla de roles (no se consulta al IdP en cada request).

<a id="identity-provider-recomendado"></a>
## Identity provider recomendado
Evaluacion por tipo de organizacion:
- SaaS B2C con soporte multiregional: Auth0 u Okta Customer Identity.
- Empresa con AD/Azure AD: Microsoft Entra ID (anteriormente Azure AD).
- Self-hosted open source: Keycloak con realm dedicado.
- Startup pequena: Auth0 Free tier hasta 7500 MAU, luego migrar.

El stack no depende del IdP concreto: basta con que exponga OIDC estandar.
La referencia canonica usada en ejemplos y configuraciones del repositorio es `Keycloak` con un `realm` dedicado por producto.

<a id="matriz-de-permisos-canonica"></a>
## Matriz de permisos canonica
Roles reales del Integration Hub (de `PlatformRoles` + `@RolesAllowed` en `platform-app` + `auth-access.service.ts` del frontend): `platform-admin`, `integration-admin`, `operator`, `payments-operator`, `auditor`, y del vertical SWIFT `pay-conflict-maker` y `pay-conflict-checker`.

| Rol | Leer catalogo tecnico | Leer procesos/ejecuciones/auditoria | Escribir catalogo | Definir procesos | Ejecutar procesos |
| --- | --- | --- | --- | --- | --- |
| platform-admin | si | si | si | si | si |
| integration-admin | si | si | si | si | si |
| operator | no | si | no | no | si |
| payments-operator | no | si | no | no | si |
| auditor | si | si | no | no | no |
| pay-conflict-maker | no | si | no | no | no |
| pay-conflict-checker | no | si | no | no | no |

### Los dos roles del four-eyes bancario

`pay-conflict-maker` y `pay-conflict-checker` no dan acceso a mas datos: gobiernan **quien puede
cerrar un conflicto de pago**. El acknowledge de un `PAY_CONFLICT` es un flujo de dos pasos
-solicitar (maker) y aprobar (checker)- y el backend **rechaza que el checker sea el mismo actor que
el maker**. Es segregacion de funciones sobre el camino del dinero, no una capa de lectura.

El flujo de dos pasos es condicional: se activa con
`mt101.pay.conflict.acknowledge.maker-checker.enabled`. Con la propiedad en `false` el acknowledge es
de un solo actor. En el entorno de integracion esta activada para homologar el flujo, y es el valor
deseado en produccion.

### Donde vive cada rol (ADR-021)

La ubicacion no es arbitraria, se deriva de la frontera motor/vertical:

- **Transversales al producto** -> `platform-spi/.../security/PlatformRoles.java`:
  `platform-admin`, `integration-admin`, `operator`, `auditor`, `payments-operator`.
- **Especificos de un estandar** -> el vertical que los define:
  `vertical-swift-mt101/.../api/security/Mt101Roles.java` declara los dos de conflictos de pago.

Un rol que solo tiene sentido dentro de un vertical **no sube al SPI**: subirlo obligaria al motor a
conocer un concepto del estandar, que es justo lo que la frontera impide.

La **matriz canonica endpoint x rol** (fuente unica, derivada del codigo) vive en
[ADR-003 - RBAC endpoint x rol](adr/ADR-003-rbac-endpoint-rol.md). La tabla de arriba es el resumen por capacidad.

<a id="instanciacion-por-stack"></a>
## Instanciacion en este producto (Quarkus + Angular + Keycloak)
- Backend Quarkus: `quarkus-oidc` valida el JWT contra el JWKS de Keycloak; la autorizacion es por endpoint con `@RolesAllowed` en los `*Resource` de `platform-app`, usando literales centralizados en `PlatformRoles` (fuente de verdad).
- Frontend Angular: `auth-access.service.ts` resuelve los roles del token de Keycloak y condiciona la UI con capacidades semanticas (`admin`, `operate`, `audit-read`, `audit-operate`, `audit-admin`); el backend sigue siendo la autoridad real (defensa en profundidad).
- IdP: Keycloak (realm `integration-hub`); ver [Configuracion y secretos](03.05-configuracion-secretos.md).

<a id="auditoria-de-eventos-de-acceso"></a>
## Auditoria de eventos de acceso
> **⚠️ NO IMPLEMENTADO — y ademas invalido tal como esta escrito.** Los tres eventos de abajo
> prescriben un campo `eventType`, pero `contracts/events/audit-log.schema.json` declara
> `additionalProperties: false` y **no tiene** ese campo: sus propiedades son `eventId`,
> `occurredAt`, `actor`, `action`, `resourceType`, `resourceId`, `outcome`, `correlationId` y
> `detail`. Un evento con `eventType` seria rechazado por el propio schema. Verificado tambien que
> **nadie los emite**: cero ocurrencias de `auth.denied`, `auth.privileged` o `auth.session.revoked`
> en el codigo.
>
> Se conserva como objetivo -la necesidad de auditar accesos es real- pero no debe citarse como
> control existente. Al implementarlo, usar el vocabulario del schema (`action` + `outcome`), no
> inventar un campo nuevo.

Cada intento de acceso fallido o privilegio elevado deberia generar un evento conforme a
`contracts/events/audit-log.schema.json`:
- `eventType=auth.denied`: cuando el token es invalido o el rol no tiene permiso.
- `eventType=auth.privileged`: cuando el usuario ejerce un permiso admin.
- `eventType=auth.session.revoked`: al hacer logout global.

Estos eventos alimentan un panel de seguridad en Grafana y reglas de alerta por anomalias (pico de denies, sesiones sospechosas).

<a id="anti-patrones"></a>
## Anti-patrones
- Emitir tokens sin `aud`: permite reutilizacion entre servicios.
- Firmar con secreto compartido (HS256) en produccion: compromete a todos los servicios con el mismo secreto.
- Hardcodear roles en el codigo sin central de verdad: genera drift.
- Guardar JWT en localStorage sin XSS hardening: preferir cookie httpOnly + SameSite=strict.
- Dejar expiracion larga (mas de 1 hora) sin rotacion: expande la ventana de abuso tras robo.
