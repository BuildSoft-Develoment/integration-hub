## Nota de uso

Este documento resume la solucion tecnica real del proyecto. Debe poder leerse junto con `ADR`, `LikeC4`, `docs/architecture/` y el plan de despliegue sin contradicciones.

## Como se instancio esta fase en Integration Hub

- El producto se implementa como una plataforma de integracion con backend `Quarkus`, frontend `Angular/Nx`, persistencia `PostgreSQL`, seguridad `OIDC/Keycloak` y observabilidad con `OpenTelemetry`.
- La UI administrativa vive en `frontend/` y se empaqueta con `Quinoa` dentro de `platform-app/`.
- La arquitectura aplica separacion por dominios funcionales y por providers para fuentes, readers, conexiones y tareas.
- La operacion y el despliegue se aterrizan en `ops/`, `ci/` y `releases/`.

## Criterio minimo de completitud

- estilo de arquitectura definido y justificado

## Estilo de arquitectura

La solucion responde hoy a un monolito modular sobre `Quarkus` con frontend desacoplado a nivel de workspace, pero integrado en despliegue. No se usa una malla de microservicios; se prioriza coherencia operacional, menor complejidad de despliegue y extensibilidad interna por providers.

## Frontend

- `frontend/` aloja un workspace `Nx` con `Angular 21`.
- La app `web` implementa la consola administrativa para `overview`, catalogos, procesos, ejecuciones, schedules y auditoria.
- La UI usa `Angular Material`, `CDK`, `TailwindCSS v4`, `Signals` y guards por seccion.
- `Quinoa` integra el build del frontend dentro del runtime `Quarkus`.

## Backend

- `platform-app/` concentra API, seguridad, scheduler, ejecucion de procesos y acceso a datos.
- El backend expone capacidades de catalogo, ejecucion, auditoria y operacion.
- La extension funcional se apoya en managers y providers por dominio en vez de plugins arbitrarios en runtime.
- La logica de integracion debe preservar trazabilidad por proceso, tarea y archivo.

## Base de datos

- `PostgreSQL` es la persistencia principal para catalogos, ejecuciones, auditoria y staging.
- La integridad de la operacion depende de correlacionar proceso, tareas, archivos y eventos.
- Las conexiones a sistemas externos pueden usar `JDBC` u otros mecanismos segun provider, pero la plataforma conserva una base interna central.

## Seguridad

- La autenticacion y autorizacion se apoyan en `OIDC` con `Keycloak`.
- La UI y la API deben respetar roles operativos como `Platform Admin`, `Integration Admin`, `Operator` y `Auditor`.
- La seguridad no se limita a login: tambien cubre secretos, permisos por seccion y auditoria funcional.

## Integraciones

- fuentes `filesystem`, `ftp`, `sftp` y `rest`
- readers por formato `txt`, `csv`, `xls`, `xlsx`, `json` y `xml`
- conexiones externas para persistencia o invocacion de servicios
- tareas configurables como `FILE_READ`, `DB_WRITE`, `REST_CALL` y `NOTIFICATION`

## Observabilidad

- la plataforma requiere logs, metricas y trazas correlacionadas
- `OpenTelemetry` cubre la base de trazabilidad distribuida
- la operacion necesita visibilidad sobre scheduler, ejecuciones fallidas, errores de integracion y rendimiento por tarea
