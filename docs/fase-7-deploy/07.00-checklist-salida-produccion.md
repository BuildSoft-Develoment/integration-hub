## Ambientes reales

No existen `PRE` ni `PRO` como tales. La escalera hoy es:

1. **dev local** — `quarkus:dev` en la laptop, servido en `/`.
2. **integracion on-premise** — build **nativo** bajo el subpath `/appih`, detras de nginx, en
   `app.buildsoft.com.pe:443`. Es el ambiente de homologacion y el que corre los casos manuales.
3. **produccion** — todavia no existe. Cuando exista, hereda de (2).

## Base de datos (bloqueante)

- [ ] **Backup restaurable verificado ANTES de desplegar.** No "existe un backup": probado que se
      puede volver con el. Esta release no es reversible solo con el artefacto.
- [ ] **Recreacion de base asumida y planificada.** ADR-023 reescribio los checksums de 53
      migraciones: una base con las anteriores aplicadas hace que Flyway **aborte el arranque**.
- [ ] **El `search_path` de la base incluye `vertical_mt101`, o el rol de la aplicacion es dueno de
      la base.** Basta con UNA de las dos. `V12` comprueba primero si ya esta fijado y, en ese caso,
      no pide ningun privilegio; solo exige la propiedad cuando tiene que fijarlo el mismo. Si no se
      cumple ninguna, un administrador ejecuta `ALTER DATABASE <bd> SET search_path = public,
      vertical_mt101;` **o** `GRANT <rol_dueno> TO <rol_app>;` y se reintenta sin tocar nada mas.
      (Ver la matriz de privilegios minimos del instalador, mas abajo.)
- [ ] **Verificacion post-arranque de los dos esquemas:**
      `select table_schema, count(*) from information_schema.tables`
      `where table_schema in ('public','vertical_mt101') group by 1;`
      Esperado: `public` con las del motor y `vertical_mt101` con 22.

### Privilegios minimos del rol de la aplicacion

Un cliente bancario no concede la propiedad de la base. Esta es la matriz medida sobre las **104
migraciones** del reactor, verificada contra PostgreSQL 16 con un rol no-dueno real, no deducida:

| Necesita | Para que | Migraciones |
|---|---|---|
| `CONNECT` sobre la base | arrancar | todas |
| `CREATE` sobre la base | `create schema vertical_mt101` | solo `V12` |
| `USAGE` + `CREATE` sobre `public` y `vertical_mt101` | tablas, indices, secuencias, funciones y triggers | todas las demas |

**Ninguna migracion pide `CREATE EXTENSION` ni ejecuta `GRANT`** (medido: 0 de 104). Las 4 que
crean funciones y las 4 que crean triggers no piden nada por encima de `CREATE` sobre su esquema, y
tampoco lo pide la unica `create sequence`.

Las **dos** unicas sentencias que exigian propiedad estan hoy guardadas y **ya no bloquean**:

| Sentencia | Exige | Comportamiento actual |
|---|---|---|
| `alter database ... set search_path` (`V12`) | dueno de la **base** | Se salta si el `search_path` ya incluye `vertical_mt101`. Solo exige la propiedad cuando tiene que fijarlo el mismo. |
| `comment on schema vertical_mt101` (`V12`) | dueno del **esquema** | Se salta si el rol no lo posee. Es metadata cosmetica; bloqueaba la instalacion cuando el DBA precreaba el esquema. |

Por tanto hay **dos formas validas de instalar**, y el checklist admite cualquiera:

1. **El rol posee la base.** No hay que hacer nada mas; `V12` fija el `search_path` solo.
2. **Minimo privilegio (el patron bancario).** El DBA precrea la base y el esquema, concede
   `CONNECT` + `CREATE ON DATABASE` + `USAGE,CREATE ON SCHEMA`, y ejecuta una vez
   `ALTER DATABASE <bd> SET search_path = public, vertical_mt101;`. Verificado de punta a punta:
   con eso, la cabecera de `V12` corre limpia sin ser dueno de nada.

## Controles bancarios (bloqueante)

Valores de `ops/fase-7-deploy/dist/config/application-prod.properties`. El efecto de moverlos esta
en [el runbook del money-path](../../ops/runbooks/008-mensajeria-pagos-runbook.md).

- [ ] `mt101.pay.conflict.acknowledge.maker-checker.enabled` = **true**
- [ ] `mt101.pay.direct-list.enabled` = **false**
- [ ] `mt101.pay.route-sink.strict` = **true**
- [ ] `mt101.build.insert-batch-max-bytes` = **200000**
- [ ] `mt101.pay.require-normal-pay-resolver` — condicional al diseno del proceso
- [ ] `mt101.pay.require-gateway-proof` — **sale apagado**. Encenderlo hace fallar pre-despacho toda
      definicion MT101_PAY REST que no declare como se prueba la aceptacion, asi que **exige migrar
      las definiciones primero**. Su encendido lo firma el responsable del money-path, no el
      despliegue.

## Build nativo

- [ ] Quarkus >= 3.37.2 y builder con >= 12 GB de RAM.
- [ ] Imagen base **`quay.io/quarkus/ubi9-quarkus-micro-image:2.0`**, con el prefijo `ubi9-`. Existen
      dos imagenes micro y solo se distinguen por ese prefijo: `quarkus-micro-image:2.0` (sin el) es
      UBI8 / glibc 2.28 y el runner muere con `GLIBC_2.34 not found`, porque el builder Mandrel
      jdk-25 es UBI9. No es "micro si o micro no" —la imagen correcta ES la micro—, es el prefijo.
- [ ] **El perfil `appih` es una decision de BUILD-TIME irreversible**: hornea el `root-path` y el
      `base-href` del SPA. Una imagen construida sin el sirve en `/` y **no funciona** detras del
      nginx de integracion; no se arregla por configuracion, hay que reconstruir.
- [ ] Health checks y observabilidad listos.
- [ ] Secretos, accesos y configuracion externa validados.
