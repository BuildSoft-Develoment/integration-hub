## Objetivo

Validar que la salida a produccion ya tiene controles minimos de calidad, release y recuperacion.

## Estado actual de la fase

- `ci/` contiene el baseline de pipeline y chequeos documentales.
- `ops/fase-7-deploy/` concentra `runbook.md`, `rollback.md` y notas por feature.
- `releases/` guarda snapshots y notas de version documentales.

## Checklist aplicado

- [ ] QA deja conclusion trazable.
- [ ] Pipeline o baseline equivalente esta revisado.
- [ ] Runbook de despliegue disponible.
- [ ] Rollback operativo disponible.
- [ ] Smoke tests definidos para cada ambiente de la escalera real (ver abajo).
- [ ] Evidencias o snapshot de release preparados.

## Ambientes reales

No existen `PRE` ni `PRO` como tales. La escalera hoy es:

1. **dev local** — `quarkus:dev` en la laptop, servido en `/`.
2. **integracion on-premise** — build **nativo** bajo el subpath `/appih`, detras de nginx, en
   `app.buildsoft.com.pe:443`. Es el ambiente de homologacion y el que corre los casos manuales.
3. **produccion** — todavia no existe. Cuando exista, hereda de (2).

## Base de datos (bloqueante)

- [ ] **Backup restaurable verificado ANTES de desplegar.** No "existe un backup": probado que se
      puede volver con el. Esta release no es reversible solo con el artefacto.
- [ ] **Recreacion de base asumida y planificada.** ADR-023 reescribio los checksums de 53
      migraciones: una base con las anteriores aplicadas hace que Flyway **aborte el arranque**.
- [ ] **El rol de base es DUENO de la base.** `V12` ejecuta `ALTER DATABASE ... SET search_path` y
      falla en voz alta si no lo es, nombrando la sentencia que debe correr un administrador.
- [ ] **Verificacion post-arranque de los dos esquemas:**
      `select table_schema, count(*) from information_schema.tables`
      `where table_schema in ('public','vertical_mt101') group by 1;`
      Esperado: `public` con las del motor y `vertical_mt101` con 22.

## Controles bancarios (bloqueante)

Valores de `ops/fase-7-deploy/dist/config/application-prod.properties`. El efecto de moverlos esta
en [el runbook del money-path](../../ops/runbooks/008-mensajeria-pagos-runbook.md).

- [ ] `mt101.pay.conflict.acknowledge.maker-checker.enabled` = **true**
- [ ] `mt101.pay.direct-list.enabled` = **false**
- [ ] `mt101.pay.route-sink.strict` = **true**
- [ ] `mt101.build.insert-batch-max-bytes` = **200000**
- [ ] `mt101.pay.require-normal-pay-resolver` — condicional al diseno del proceso
- [ ] `mt101.pay.require-gateway-proof` — **sale apagado**. Encenderlo hace fallar pre-despacho toda
      definicion MT101_PAY REST que no declare como se prueba la aceptacion, asi que **exige migrar
      las definiciones primero**. Su encendido lo firma el responsable del money-path, no el
      despliegue.

## Build nativo

- [ ] Quarkus >= 3.37.2 y builder con >= 12 GB de RAM.
- [ ] Imagen base **UBI9**. La variante micro es UBI8 (glibc 2.28) y el runner no arranca.
- [ ] **El perfil `appih` es una decision de BUILD-TIME irreversible**: hornea el `root-path` y el
      `base-href` del SPA. Una imagen construida sin el sirve en `/` y **no funciona** detras del
      nginx de integracion; no se arregla por configuracion, hay que reconstruir.
- [ ] Health checks y observabilidad listos.
- [ ] Secretos, accesos y configuracion externa validados.
